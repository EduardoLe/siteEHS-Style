# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Google Apps Script web app (EHS — Environment, Health & Safety dashboard for a manufacturing
plant): a backend in `Code.gs` that reads/aggregates data from ~10 Google Sheets, and a
frontend SPA in `Index.html` served via `doGet()` and consumed through `google.script.run`.
There is no framework, no package manager, no build step, and no automated test suite — this
is the standard Apps Script deployment model (editor → "Implantar"). See `BRIEFING.md` for a
full architecture/data-model inventory generated by mapping the codebase; treat it as a
reference, not as always up to date with the latest session's changes.

## Commands

There is no npm/build/lint/test tooling checked into this repo. What you actually have:

- **Syntax-check the frontend JS** (the only automated check available — Apps Script files
  aren't a recognized Node extension, so extract the embedded `<script>` first):
  ```bash
  node -e "
  const fs = require('fs');
  const html = fs.readFileSync('Index.html', 'utf8');
  const script = html.match(/<script>([\s\S]*?)<\/script>/)[1];
  fs.writeFileSync('/tmp/extracted.js', script);
  "
  node --check /tmp/extracted.js
  ```
  Do the same for `Code.gs` by copying it to a `.js` file and running `node --check` on that.
- **Manual/visual testing**: `Index.html` embeds a full mock of `window.google.script.run`
  (activates automatically when `google` is undefined, i.e. opening the file directly in a
  browser instead of through Apps Script `/exec`). Open the file locally and use browser
  devtools — this is the primary way to verify frontend changes without deploying.
- **Deploying**: happens through the Apps Script editor (clasp is not configured in this repo).
  `git push` only updates GitHub — it has **no effect on the live site**. To ship a change you
  must copy the updated `Code.gs`/`Index.html` into the Apps Script editor, save, then
  **Implantar → Gerenciar implantações → editar a implantação ativa → Nova versão → Implantar**.
  A stale deployment after a code fix looks exactly like the bug you just fixed (same console
  error) — if a fix "didn't work" after a push, check whether it was actually redeployed before
  re-diagnosing.

### Rebuilding the compiled Tailwind CSS

Tailwind is **not** loaded from CDN — the `<style>` block near the top of `Index.html` (search
for `Tailwind CSS: build COMPILADO E TRAVADO`) is a locally-compiled, pinned, minified Tailwind
v3 build pasted inline, scanning `Index.html` itself for classes used. **Any time you add or
change a Tailwind utility class in the HTML, you must rebuild and re-paste this block, or the
new class will silently have no effect** (this has bitten this project more than once). There
is no `tailwind.config.js`/`package.json` checked into the repo for this — set one up ad hoc
(content: `["Index.html"]`, theme colors: `brand-primary #0d436b`, `brand-secondary #00a0dd`,
`brand-bg #edf4fc`, matching `EHS_CORES_` in the frontend `<script>`), run
`tailwindcss -c tailwind.config.js -i input.css -o output.css --minify`, and replace the
contents of that `<style>` block with the output.

## Architecture

### Backend (`Code.gs`, ~9.7k lines, ~200 functions, single file)

No file-level module boundaries — organized by comment-delimited sections. Key conventions:

- **Column resolution by header name, not position.** Sheets are read by matching exact header
  text (`localizarColuna_`, `resolverColunaPorNomeOuPosicao_`), with an explicit thrown error
  when a required column is missing — this is a deliberate project-wide convention, not an
  oversight. A few documented exceptions read fixed cells/columns positionally (e.g. `OL Taxas`
  reads fixed cells `AW162`/`F162`; `SAF Auditoria` column E is unlabeled by design).
- **Standard `get*` function shape**: build a `vazio` fallback object → check cache (unless
  `forcar`) → compute → best-effort cache write in its own `try/catch` → return. On error, set
  `vazio.erro` and return that instead of throwing — these functions must never throw across
  the `google.script.run` boundary, since a thrown error there just shows a generic failure to
  the user with no detail.
- **Caching**: `CacheService` wrapped with chunking helpers (`cacheGravarGrande_`/
  `cacheLerGrande_`) to work around the 100KB per-key limit, with TTLs per data source (mostly
  1.5h–6h).
- **`_` suffix** marks "private" (not part of the `google.script.run` public surface) — this is
  not just a naming convention, it's a real constraint: a function ending in `_` is unreachable
  from the frontend in the deployed Apps Script runtime (`google.script.run...xyz_ is not a
  function`), even though it works fine in the `Index.html` dev-mode mock, which doesn't enforce
  this. Any new function the frontend calls directly via `google.script.run` must NOT end in `_`
  (this shipped broken once already — see git history around `getApontamentosNovo`).
- **`debug*` functions** (dozens of them) are manual diagnostics run from the Apps Script
  editor, not part of the request/response flow — a deliberate, well-established convention.
- Secrets live in `PropertiesService.getScriptProperties()` (`ANTHROPIC_API_KEY`,
  `PRUDENCIO_FAVICON_URL`, `campanhasPlanilhaId`), never hardcoded.

### Google Sheets as the database

~10 distinct spreadsheets are referenced by ID constants, several of which are the **same
physical workbook under different constant names** for different tabs (e.g. Cruz Verde ≡
Ocorrências ≡ ATS ≡ Base pessoas; TAG Safety ≡ Programa TAG). Check `BRIEFING.md` §4 before
assuming two `*_SPREADSHEET_ID_` constants are different sheets. Three separate TAG-related
data sources currently coexist and are easy to confuse:

- `TAG_SAF_SPREADSHEET_ID_` ("BASE TAG - SAF", ~65k rows) — feeds the Pirâmide de Segurança only.
- `PROGRAMA_TAG_SPREADSHEET_ID_` ("Respostas ao formulário 5") — feeds the Home "TAGs
  registradas" KPI tile, aggregated across all 6 vertentes of the TAG program (Safety, Ver e
  Agir, Professional/Autonomous Maintenance, Environment, Workplace Organization).
  `obterResumoProgramaTag_`.
- `APONTAMENTOS_NOVO_SPREADSHEET_ID_` ("BASE DE ENVIO") — the newest source (added 2026-09-20),
  Safety-only, feeds the rebuilt Apontamentos tab exclusively. `getApontamentosNovo`.

Don't assume these are interchangeable or that consolidating them is safe without checking
what each one's consumer actually expects (scope differs, not just source).

### Frontend (`Index.html`, single file, ~8.8k lines)

`<head>`/config, inline `<style>` (compiled Tailwind + hand-written custom CSS), markup, then
one large `<script>` block with plain global functions (no framework, no bundler). DOM is
manipulated via `innerHTML`/`createElement`; all charts are hand-drawn SVG (no charting
library) — look at `desenharFaiRec_`, `desenharParetoObjeto_`, or the donut-chart code for the
established patterns (3D-prism bar charts via depth-vector polygons, gradient+gloss-overlay
donuts, `feDropShadow` line charts) before inventing a new chart style.

- **Panel/tab visibility**: elements are tagged `data-aba="<nome>"` and shown/hidden in bulk by
  `mostrarAbaMetrics(nome)`, which unconditionally un-hides every matching block on tab switch.
  If a block needs state that survives across tab switches (e.g. a loading spinner that should
  stay hidden once data has loaded), you must resync it after `mostrarAbaMetrics` runs — see
  `apontSincronizarEstadoAba_` for the pattern used to fix exactly this bug in the Apontamentos
  tab.
- **`google.script.run` calls**: always pair `.withSuccessHandler`/`.withFailureHandler`. Follow
  the existing `carregar<X>_()`/`renderizar<X>_()` split (fetch-and-cache-once vs. render) used
  throughout (`carregarAts_`, `carregarOcorrenciasPainel_`, `carregarApontamentosNovo_`, etc.).
- **Dev-mode mock**: a full mock of `window.google.script.run` lives inline in the same
  `<script>` block and auto-activates when `google` is undefined. When adding a new
  `google.script.run.X()` call, add a matching mock entry with the same shape (including
  realistic edge cases) so the feature is testable by opening the file directly in a browser.
- Search/filter UI (detail tables with a text search + `<select>` filters) follows one
  established pattern across ATS, Ocorrências, and Apontamentos: populate `<select>` options
  from distinct values in the loaded data, normalize search text, combine active filters with
  search terms, cap rendered rows, and show an active-filter count + "clear filters" affordance.
- **The deployed site runs inside an iframe Google controls** (`userCodeAppPanel` in the
  console/URL — not something this repo's markup can add attributes to). Confirmed 2026-09-20
  with an isolated sandboxed-iframe test: `speechSynthesis.speak()` (Web Speech API text-to-
  speech) works fine from inside it, but `getUserMedia`/`SpeechRecognition` (microphone) is
  hard-blocked by Permissions Policy — the wrapper `<iframe>` has no `allow="microphone"`, and
  nothing in this codebase can add one. Don't attempt voice *input* features; voice *output* is
  fine (see `criarBotaoLeituraFeed_`, the read-aloud icons on Tracker Overview cards).
- **One-time UI hints**: `mostrarDicaAffordance_` is the established pattern for "teach the
  user this is clickable" — shows once per browser (localStorage flag, wrapped in try/catch so
  a blocked/private-mode store degrades to "never shows" instead of erroring), auto-dismisses
  on a timeout or the next click anywhere. Reuse it rather than inventing a new onboarding
  mechanism.

### Prudêncio (AI assistant)

An embedded chatbot using the Anthropic API (tool-use/agentic loop) with a rule-based fallback
when the API is unavailable, grounded only in data already shown on the dashboard cards
(read-only — it does not write to any spreadsheet). Entry points: `prudencioPerguntar`,
`prudencioPerguntarInterno_`, `prudencioFerramentas_`.

- **Tools are thin wrappers over existing `get*` functions**, never new spreadsheet access —
  each entry in `prudencioFerramentas_()` calls a `get*` already backing some dashboard card and
  reshapes its output for the model, occasionally with a small inline aggregation (e.g. summing
  a nested `porAreaMes` structure down to one row per area, as `partes_do_corpo_por_area` does).
- **`<algo>_por_area` naming convention**: tools that answer "how's area X doing" return the
  full breakdown grouped by area — no `area` input parameter — and let the model pick the right
  row itself (mirrors the original `ocorrencias_por_area`). Don't add server-side area
  filtering; the payloads here are small (a handful of areas, not thousands of rows), so the
  model self-filtering is simpler and consistent with the existing tools.
- Keep `prudencioSaudacaoInicial()`'s greeting text in sync with what tools actually exist — it
  lists topics the assistant claims to cover, and it has drifted out of sync before (claimed
  "partes do corpo" with no backing tool until 2026-09-20).
- **The AI path and the no-API rule-based fallback are two SEPARATE registries** —
  `prudencioFerramentas_()` (tools the model can call) vs `prudencioIntencoes_()` (keyword
  triggers matched in `prudencioResponderSemIa_`). Adding a tool does NOT make the rule-based
  engine aware of it; this shipped broken once (2026-09-20 — 3 new area tools worked for the AI
  path but "como está a logística" still hit the rule engine's generic "não sei responder",
  since nothing in `prudencioIntencoes_()` recognized area *names*, only generic words like
  "área"/"setor"). When adding a capability meant to work without an API key, update both.
- **Area-name recognition without an LLM** (`prudencioAreasConhecidas_`/`area_especifica`
  intent): area names used as match terms are pulled live from the same `get*` calls the tools
  use, never hardcoded — a renamed/new area in the spreadsheet shows up automatically instead of
  silently failing to match (same lesson as the RISK header-rename bug). Names are deduplicated
  by their `prudencioNormalizar_`-ed form so accent-inconsistent spellings across sources (e.g.
  "Logística" vs "Logistica") collapse into one.

## Working conventions established in this repo

- Prefer fixing the actual missing/renamed column over adding a silent fallback — this
  codebase's existing pattern is to throw a clear, named error listing what was expected
  when a required header is missing, not to guess or default.
- Don't consolidate the duplicated BR-locale date/number parsers or column-resolution helpers
  opportunistically — several exist for historical reasons (see `BRIEFING.md` §6); consolidate
  only when it's the actual task at hand, and keep old names as thin wrapper aliases if other
  code still calls them, rather than doing a mass rename.
- Architectural changes to this repo (new data sources, new subsystems) go through a written
  design spec first — see `docs/superpowers/specs/` for the existing spec format and process.
- When a card/panel shows "no data" with no visible JS error, it's almost always the backend's
  `get*` function returning `{ erro: "..." }` (by design — see "Standard `get*` function shape"
  above), not a frontend bug. Check the `.erro` field first (e.g. via `debug<X>_()` in the Apps
  Script editor against the live sheet) before assuming the fix is in `Index.html`. A recurring
  root cause: someone renamed a column header in the source spreadsheet upstream, and
  `indiceColuna_`'s exact-match lookup silently stopped finding it (fixed exactly this in
  `getRiscosAltos` on 2026-09-20 — "Quantidade" → "Quantidade Riscos").
